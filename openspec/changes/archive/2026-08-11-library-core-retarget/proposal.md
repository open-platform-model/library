# Proposal — library-core-retarget

## Why

Enhancement 0010 moved the OPM core schema to a new major: `opmodel.dev/core@v2`, published on GHCR with `v2.0.0-alpha.4` as the first complete tag on the line — alpha.1–alpha.3 are partial cuts that resolve but lack the identity package (alpha.5, carrying only the publish-side D49 gate amendment, trails a release-metadata fix and is equally complete once cut). The library still consumes `opmodel.dev/core@v1` (retired at `v1.1.0-alpha.1`). Every remaining 0010 library slice (`library-acquire-and-subscription`, `library-matching`) and both downstream repos (`cli`, `opm-operator`) depend on this crossing landing first.

This is an **import rewrite, not a re-pin**: a major crossing that `task update-deps` cannot perform. The runtime retarget itself is one constant (`schema.DefaultSchemaModule`), but the test fleet must move with it, because a module or catalog evaluates against the core version its own `cue.mod` declares — v1-authored fixtures cannot unify with v2-typed values at render seams.

**This is the second landing.** The first (library#51) shipped the crossing against a library-owned stand-in fixture catalog, because 0010's ordering then placed the real catalogs' v2 authoring behind the library slices and no v2-built catalog existed. It was reverted the same day (library#52): the stand-in duplicated the real catalog's shape knowledge with no named retirement owner. 0010 inverted the ordering instead — catalogs moved first. Since then `catalog_opm` has become the single first-party catalog (D47, absorbing `catalog_kubernetes` as the `k8s-*` raw family and `catalog_opm_experimental` at `v1alpha1`), adopted D49's `<kind>/<apiVersion>/` versioned filing, and released the consolidated result on its v2 line (`2.0.0-alpha.1` authoring, `2.0.0-alpha.2` consolidation) via release-please. The redo re-lands the crossing against that real catalog, carries forward library#51's seam adaptations and major-aware fixture writers, and drops the fixture catalog, its disk-registry publish helper, and the vet-skip guard.

This change is 0010's `library-core-retarget` slice (see `enhancements/0010/plan.yaml`). Its decisions: D42, D47, D49.

## What Changes

- **`schema.DefaultSchemaModule` flips to `"opmodel.dev/core@v2"`.** The floating-major mechanism is unchanged: the existing bare-major expansion in `OCILoader.loadVersioned` resolves the latest version within the major (today `v2.0.0-alpha.4`; alpha.5 when it cuts; the `-0.dev.*` tags sort below the alphas by SemVer, so they never win). After the crossing, alpha bumps within v2 are ordinary `task update-deps` work again.
- **Test fixture writers become major-aware** (re-land from library#51). `opm/internal/registrytest` hardcodes `core@v1` in the deps line, the catalog import, and the module-path major; these derive from the fixture's (defaulted) core version instead, so v2-defaulted and v1-pinned fixtures coexist. `defaultCoreVersion` moves to `v2.0.0-alpha.4`; writer defaults emit the v2 shape.
- **Mainline fixtures re-land against the real consolidated catalog.** `testdata/modules/web_app` moves to core v2 with its catalog dep re-pointed at `opmodel.dev/catalogs/opm@v2` (the consolidated `2.0.0-alpha.2` or newer) and its imports moved to the D49 versioned packages — `…/blueprints/v1beta1`, `…/traits/v1beta1`, `…/resources/v1beta1` — not the flat `…/blueprints` target library#51 used, which D49 amended before it could ship. `modules/opm_platform` re-keys its subscription to the major-suffixed `opmodel.dev/catalogs/opm@v2` with the required scalar `version:` pinned to the newest tag on the v2 line (`#SubscriptionFilter` no longer exists in v2). `testdata/` and the kernel flow/synth fixtures reauthor to the v2 identity shape.
- **Four address-seam adaptations, each strictly input-extending** (v1 inputs byte-identical). Three re-land from library#51: materialize's pull decomposes the major-suffixed `#registry` key before composing the load ID (`…@v2@v2.0.0-alpha.2` is not a loadable ID); synth's module-import derivation passes a v2 `modulePath` through verbatim (it IS the import path, D1); `materialize/cache.Key` adds the scalar `version` to the normalized projection so two v2 platforms differing only in it stop sharing a key. The fourth is new, forced by the real catalog: **version enumeration is scoped to the subscription key's major.** The `catalogs/opm` OCI repo carries every line's tags — including stable `v0.5.2`/`v0.6.0` — and a v2 subscription has no filter, so the unscoped no-filter default would select stable `v0.6.0`, a core-v0 catalog (the exact hazard the v1 fixture's `filter: range:` comment documents). A key carrying `@vN` now enumerates within major N; major-free (v1) keys are unchanged.
- **No fixture catalog.** `modules/opm_catalog`, the registrytest disk-tree publish helper, the `testing.opmodel.dev` routing, and the cue:vet skip guard from library#51 are not re-landed. In-process `registrytest` inline `#Catalog` fixtures remain the hermetic path for materialize/kernel tests; the flow tests that materialize a published catalog materialize the real one from GHCR, as they do today on the v1 line.
- **Historical pinned tests are kept unchanged**: the v0.5.2 closedness canary (`composed_open_test.go`), the library#31 regression (pinned to `catalogs/opm@v0` v0.6.0), and the synth boundary tests (`pinnedCache("v1.0.0-alpha.1")`) — each pins both its fixture core dep and its schema cache coherently, independent of the default. The `docs/design/repro-hidden-field/` repro stays pinned to v1 (it reproduces a v1-era bug).
- **No behaviour change for previously-expressible inputs.** The subscription-selection, matching, and identity-read semantics are untouched for v1 artifacts; the seam adaptations only make v2 addresses readable. Two transitional invariants make that safe (see design).

**Recorded deviation from 0010's plan (stands from the first landing):** the original D42 concern named "two import sites." The one at `instance_integration_test.go:154` does **not** move — it imports `blueprints/workload` from catalog v0.6.0, where blueprints genuinely live one segment deep; moving it while pinned there would break the fixture. Only the `web_app` site moves, now to the D49 versioned path. Recorded in 0010's history 2026-08-10.

### Modified Capabilities

- `schema-dispatch`: the single consumed schema module becomes `opmodel.dev/core@v2`; default-resolution and resolved-version scenarios move to the v2 line. Loader mechanics (interface, OCILoader, Cache) are unchanged.
- `platform-materialization`: subscription resolution becomes major-aware — a `#registry` key carrying the v2-mandatory `@vN` suffix enumerates and selects within that major; major-free keys keep today's whole-repo behaviour.

## Impact

- **`opm/` public surface:** `schema.DefaultSchemaModule` value changes (`@v1` → `@v2`). No signature changes.
- **SemVer: breaking** (Principle VI). A consumer relying on the default loader now resolves core v2, whose `#Module`/`#Catalog` shapes reject v1-authored artifacts. Ships as `feat!:` with a `Migration: library-core-retarget` trailer and a `MIGRATIONS.md` `## Unreleased — Breaking` entry (recipe: pin `schema.OCILoader{Module: "opmodel.dev/core@v1.0.0-alpha.1"}` to stay on v1; rollback is the same rewrite in reverse to `v1.1.0-alpha.1`).
- **Downstream:** `cli` and `opm-operator` pick this up via their own retarget slices (`cli-coordinate-adoption`, `operator-library-retarget`); neither consumes this release until then.
- **Packages touched:** `opm/schema` (one constant + doc comments), `opm/materialize` (pull decomposition, major-scoped enumeration, cache key), `opm/helper/synth` (import derivation), `opm/internal/registrytest`, `opm/internal/schematest` (comments), test files under `opm/kernel/`, `opm/helper/synth/`, `opm/materialize/`, plus CUE fixtures (`testdata/`, `modules/opm_platform`) and docs (`CLAUDE.md`, `Taskfile.yml` comments, `MIGRATIONS.md`).
- **Scope note (Principle VIII):** the crossing is atomic — the default flip and the mainline-fixture move must land together or the suite breaks — but the tasks stage every preparatory step (major-aware writers, seam adaptations) as independently green commits, leaving the atomic step as small as the crossing allows. Splitting further means splitting the slice, which 0010's plan sized as one; the seam adaptations were proven green-in-isolation in library#51.
